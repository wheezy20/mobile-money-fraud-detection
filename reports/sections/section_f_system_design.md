Section F: System Design
F.1 System Context
The fraud detection model from Sections C and D must operate within the realities of mobile money infrastructure in Ghana: MTN MoMo and Vodafone Cash process millions of transactions daily, often through agent networks in low-bandwidth environments, with regulatory oversight from the Bank of Ghana. Section A established the core stakeholder tensions, operators need recall to minimise losses, customers need low false positive rates to avoid blocked legitimate transactions, regulators need auditability, and fraud teams have limited review capacity. Section F translates these constraints into deployable infrastructure.
The system described here is not the production system of a Tier 1 operator (which would involve dedicated streaming platforms, multi-region replication, and seven-figure annual infrastructure budgets). It is a realistic baseline for a mid-sized operator or a fintech challenger entering the market, where every architectural decision must be defensible on cost, latency, and operational simplicity grounds.
F.2 High-Level Architecture
The system decomposes into seven components that mirror the data flow from transaction initiation to fraud decision and post-decision learning:
1. Transaction Ingestion Gateway. Mobile money switches (USSD gateway, agent app backend, partner APIs) emit transaction initiation events to a Kafka topic, transactions.raw. Kafka is chosen over a synchronous HTTP queue because it provides durable buffering: if the fraud scoring service degrades, transactions are not dropped, they wait. This is essential for an LMIC context where intermittent infrastructure issues are routine.
2. Feature Computation Service. A lightweight Python service consumes from transactions.raw, computes the engineered features defined in src/preprocessing.py (drainage ratio, error_orig, error_dest, hour_of_day, is_unusual_hour, type_encoded, amount_log), and writes the feature vector to a low-latency cache (Redis). For the production version, this service also looks up backward-looking aggregations (recipient_count_24h) from a feature store, since computing these on every request would be too slow. The feature store (PostgreSQL with materialized views, refreshed every 5 minutes) holds rolling aggregates per recipient.
3. Model Serving Layer (FastAPI + Docker). The FastAPI service from Phase 2 wraps the tuned Random Forest model, exposing /predict and /predict_batch endpoints. Multiple replicas run behind a load balancer (HAProxy or nginx). The service is stateless: any replica can serve any request, and replicas can be scaled horizontally based on load. Latency target: 50ms p99, leaving 450ms of the 500ms transaction authorisation budget for everything else.
4. Decision Layer. A thin orchestration service receives the fraud probability from the model and applies operator-configurable thresholds. Above 0.95 probability the transaction is blocked outright; between 0.70 and 0.95 it is flagged for review and the customer receives a confirmation prompt; below 0.70 it proceeds. Thresholds are configurable per transaction type and per amount tier, so a small CASH_OUT and a large TRANSFER receive different scrutiny.
5. Investigation and Audit Storage. Every scored transaction (features, model version, predicted probability, threshold applied, decision taken) is written to a PostgreSQL audit table with a 7-year retention period to satisfy Bank of Ghana audit requirements. Investigators query this through an internal Streamlit dashboard.
6. Pipeline Orchestration (ZenML + MLflow). Phase 4's ZenML pipelines run on a scheduled basis (weekly retraining, daily monitoring) on a dedicated training VM. New models pass through the conditional deployment gate (PR-AUC threshold) before being promoted to the serving layer.
7. Monitoring and Observability. Prometheus scrapes metrics from FastAPI (latency, throughput, error rate) and from the model service (prediction distribution, feature drift). Grafana dashboards visualise these. Alerts fire to PagerDuty for on-call response.

F.5 Scaling Considerations
The architecture scales along three axes:
Horizontal scaling of stateless services. The FastAPI model service and feature service are stateless, so adding replicas behind the load balancer is the primary lever. At 5M transactions/day with 50ms latency, four replicas at ~600 RPS each handle peak load comfortably. At 50M/day (10x growth), the stack scales to ~40 replicas plus a Kafka cluster expansion to 9 nodes. Cost scales roughly linearly until network egress becomes the binding constraint, typically around the 100M/day mark.
Vertical scaling of stateful components. PostgreSQL and Redis hit limits sooner. The audit table grows at roughly 600 GB per year at 5M transactions/day. Beyond two years of retention, the system needs partitioning (monthly partitions on transaction_timestamp) and cold storage for older partitions in object storage. Redis hits memory pressure on the feature store cache around 50M/day; the next step is sharding by nameDest hash.
Model complexity scaling. The current Random Forest with 200 trees serves predictions in under 50ms, but its memory footprint (~80 MB serialised) becomes a constraint when running many replicas. At 50M/day scale, the serving layer benefits from migrating to a smaller XGBoost or LightGBM model with similar PR-AUC but a 5-10x smaller memory footprint. ZenML's pipeline structure makes this swap a single-step change, the architecture does not change.
F.6 Monitoring Plan
Production fraud detection demands four monitoring dimensions, each with a clear failure mode and a clear response:
Service health. FastAPI exposes /health and /metrics endpoints. Prometheus scrapes every 15 seconds. Alerts fire on: p99 latency over 100ms for 5 minutes, error rate above 0.5%, or replica count below 2. These page the platform on-call. Response: scale replicas, investigate downstream dependencies.
Data drift. Feature distributions are compared to a reference distribution (the training set) using Population Stability Index (PSI) computed daily on a 24-hour rolling window. Alerts fire when PSI exceeds 0.2 on any feature, indicating significant distribution shift. This typically catches issues like a new agent network onboarding (changes drainage_ratio distribution) or a new fraud pattern emerging (changes amount_log distribution). Response: data science team investigates whether retraining is needed.
Model performance. The audit log lets us measure ground-truth model performance once labels arrive (typically 24-72 hours after the transaction, when fraud reports are filed). Daily PR-AUC on the previous day's transactions is computed and tracked. Alerts fire when PR-AUC drops more than 0.05 from the rolling 7-day average. Response: trigger ZenML retraining pipeline, evaluate whether to roll back to the previous model version.
Business impact. Two business KPIs are tracked daily: total fraud losses (sum of transaction values where isFraud=1 and decision=allow) and false-positive friction rate (count of decision=block where ground truth turns out to be legitimate, divided by total blocks). These are reviewed weekly with the fraud operations team and inform threshold adjustments.
F.7 Trade-offs and Limitations
The design above makes deliberate compromises that warrant explicit acknowledgement.
The system is not real-time in the streaming-analytics sense (e.g., Flink or Spark Streaming). Feature aggregations refresh every 5 minutes, which means a fraudster exploiting a brand-new mule account benefits from up to 5 minutes of stale features before recipient_count_24h reflects their activity. A streaming feature pipeline would close this gap but adds significant operational complexity that is hard to justify until the fraud team can demonstrate this 5-minute window is being actively exploited.
The Random Forest model is treated as a black box at inference time. While it is more interpretable than a neural network, regulator-grade explainability (per-prediction SHAP values, counterfactual explanations) is not part of the serving path. For the Bank of Ghana audit case, SHAP values can be computed offline from the audit table on demand. This is a deliberate trade-off: in-line SHAP would add 50-100ms to every prediction.
Finally, the system lacks an active learning loop. New fraud patterns discovered by the investigation team should ideally feed back into training data with priority sampling. The current architecture supports this but does not automate it; investigators flag transactions in the dashboard, and a weekly batch job pulls these into the next training run. A more sophisticated system would close this loop automatically, but the engineering effort is not justified at current scale.

Section E: Production Engineering & Deployment (Draft)
E.1 Overview
Section E translates the trained fraud detection model from Sections C and D into production infrastructure. The four phases address distinct concerns: experiment tracking and reproducibility (MLflow), low-latency serving (FastAPI), environment portability (Docker), and pipeline orchestration with lineage (ZenML). Together they form the minimum viable MLOps stack for an LMIC fintech where regulatory audit, intermittent connectivity, and cost-constrained infrastructure shape every decision.
E.2 Phase 1: Experiment Tracking with MLflow
MLflow was integrated to address a problem visible in Section D's hyperparameter tuning: without systematic tracking, comparing the 24 Random Forest configurations explored during grid search becomes a manual exercise prone to error. MLflow's autologging captures every fit call's parameters, metrics, and resulting model artifact, producing a queryable history of all experiments.
The tracking server runs locally with a file-based backend (./mlruns), chosen over a remote tracking server for two reasons. First, a self-contained file backend means the marker can clone the repo and reproduce the experiment ledger without provisioning infrastructure. Second, in an LMIC deployment context, an embedded MLflow store is the realistic starting point before a team has the operational maturity to run a tracking server with proper backup and access control.
Key metrics logged per run: accuracy, precision, recall, F1, ROC-AUC, PR-AUC, and the four cells of the confusion matrix. PR-AUC is treated as the primary selection metric because the dataset's fraud rate (well under 1%) makes ROC-AUC misleadingly optimistic, a model that predicts "not fraud" for everything achieves ROC-AUC near 0.5 but PR-AUC near zero.
E.3 Phase 2: Real-Time Serving with FastAPI
The serving layer wraps the tuned Random Forest in a REST API exposing two endpoints: /predict for single-transaction scoring and /predict_batch for vectorised batch scoring. FastAPI was chosen over Flask for three reasons relevant to the fraud detection context: (1) async request handling, which matters when downstream systems (mobile money switches) may issue thousands of concurrent scoring requests during peak transaction windows, (2) automatic OpenAPI schema generation, which gives mobile money operators a self-service integration path without the model team writing API documentation manually, and (3) Pydantic input validation, which catches malformed transaction payloads before they reach the model and produce silent garbage predictions.
The API loads the serialised model (models/tuned_rf.pkl) and the fitted preprocessor at startup, not per-request, to avoid the 200+ millisecond deserialisation cost on every call. Latency targets in mobile money authorisation flows are typically under 500ms end-to-end, so the model server's contribution must stay well below that, ideally under 50ms.
E.4 Phase 3: Containerisation with Docker
The Docker layer addresses environment portability. The training environment (Ubuntu 22.04, Python 3.11, scikit-learn 1.5) must be reproduced exactly wherever inference runs, otherwise subtle differences in numpy or scikit-learn versions can change predictions on edge cases. The repository defines two services in docker-compose.yml: the FastAPI inference container and an MLflow tracking server, networked together so MLflow run IDs from training can be referenced by the inference service.
The Dockerfile uses a slim Python base image to keep the deployable size manageable, an important consideration for LMIC deployments where bandwidth for image pulls is genuinely scarce and ECR-equivalent egress costs are non-trivial. Multi-stage builds were considered but rejected for this iteration as the size savings did not justify the additional Dockerfile complexity for a course project.

E.6 Integration and Trade-offs
The four phases compose into a workflow that could plausibly run in a real fintech: ZenML orchestrates training pipelines that log to MLflow, the highest-PR-AUC model is containerised and served via FastAPI, and Docker Compose lets the whole stack run locally for development or be ported to Kubernetes for production. The stack is deliberately conservative, no streaming, no feature store, no model monitoring, because each of those adds operational burden that a small fintech engineering team cannot absorb on day one. Section F discusses how this baseline evolves as the system matures.
